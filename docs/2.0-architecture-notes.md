# Pikachu Volleyball 2.0 Architecture Notes

## Product constraints

Pikachu Volleyball 2.0 remains a JavaScript, PixiJS, Webpack, and Electron project. The original game simulation and rendering are protected behavior. Architecture changes should solve a demonstrated integration or maintenance problem rather than introduce a new framework for its own sake.

## Current structure

- `src/resources/js/physics.js` owns simulation and user-input data structures.
- `src/resources/js/view.js` owns Pixi rendering.
- `src/resources/js/pikavolley.js` coordinates game states, input, physics, audio, and rendering.
- `src/resources/js/ui.js` owns the current DOM toolbar, settings, overlays, and persistence.
- Locale-specific static HTML pages are emitted by Webpack.
- `desktop/main.js` wraps the static build in Electron and currently duplicates some renderer commands through a native menu.

## 2.0 direction

1. Preserve the simulation boundary. Do not rewrite physics or AI as part of menu or input work.
2. Introduce only the minimum semantic input abstraction required to support multiple bindings and shared menu navigation.
3. Replace the permanent toolbar and duplicated Electron gameplay menu with one accessible HTML overlay aligned to the game canvas.
4. Keep desktop-only operations behind a narrow preload bridge. Do not use `executeJavaScript()` or synthetic DOM clicks for application commands.
5. Preserve static locale output while reducing duplicated locale registration and page structure after the final menu text is stable.
6. Measure bundle, startup, and AppImage changes before optimizing or upgrading dependencies.

## Decision gates

- Approve a visual menu prototype before full integration.
- Add Catalan only after the menu information architecture is stable.
- Perform packaging-sensitive validation with a real AppImage before release.
- Use Codex only when a task becomes genuinely broad, repetitive, or tightly coupled across many files; otherwise implement directly through the repository workflow.

## Branching

- `v2` is the integration branch.
- Task branches use `v2-<task>` because Git references cannot contain both a branch named `v2` and child branches named `v2/<task>`.
- Task pull requests target `v2`.
- The final release pull request targets `main` from `v2`.
