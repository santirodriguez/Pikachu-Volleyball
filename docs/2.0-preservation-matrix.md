# Pikachu Volleyball 2.0 Preservation Matrix

This document is the regression baseline for the 2.0 development cycle. A feature may be reorganized internally, but its accepted behavior must remain available unless a later task explicitly changes the requirement.

| Area | Current behavior to preserve | 2.0 expectation | Validation |
|---|---|---|---|
| Physics | Existing collision, movement, ball, net, ground, and scoring calculations | No behavioral change without an approved requirement and regression evidence | Deterministic tests where practical; manual match checks |
| AI | Existing computer-player behavior and side selection | Preserve current decisions and difficulty characteristics | Deterministic scenarios where practical; manual matches |
| Timing | 25 FPS default, slow-motion behavior, existing state timings | Preserve gameplay rhythm and transition timing | Automated state checks plus manual play |
| Game flow | Intro, mode selection, rounds, scoring, match end, and automatic AI-versus-AI inactivity flow | Same playable flows after UI integration | Web and Electron smoke tests |
| Default controls | Player 1: D, G, R, V, Z, F. Player 2: arrows and Enter | Preserve all defaults; add ControlLeft as an additional Player 1 Power Hit binding | Input tests and manual keyboard checks |
| Quick rematch | Power Hit starts a new match after the game-end delay | Preserve behavior and discoverability hint | State test and manual match completion |
| Practice mode | Practice toggle changes match behavior | Preserve behavior through the integrated menu | Automated option test and manual check |
| Practice reset | B resets the ball during practice | Preserve B binding and practice-only guard | Input/state test |
| Graphics | Sharp and soft rendering modes | Preserve choice and persistence | DOM/style test and visual check |
| BGM | On and off options | Preserve choice and persistence | Audio state test and manual check |
| SFX | Stereo, mono, and off options | Preserve choice and persistence | Audio state test and manual check |
| Speed | Slow, medium, and fast options | Preserve frame-rate choices and gameplay effect | Option test and manual check |
| Winning score | 5, 10, and 15 point targets with existing guards | Preserve options, notices, and match rules | State and UI tests |
| Settings persistence | Existing localStorage keys retain user preferences | Read existing values and migrate safely if a new schema is introduced | Migration tests |
| Accessibility | Keyboard navigation, focus visibility, ARIA states, and semantic dialogs | Preserve or improve throughout the new menu | Keyboard test, accessibility inspection, manual check |
| Color scheme | Light, dark, and system-aware outer UI behavior | Preserve where outer UI remains visible | Browser check |
| PWA and offline | Static web build can install and run offline | Preserve service-worker behavior and static locale routes | Build inspection and offline browser check |
| Audio startup | Critical rendering is not blocked by audio loading | Preserve deferred audio warm-up | Startup smoke test |
| Electron startup | Direct locale loading, hidden-until-ready window, no white redirect screen | Preserve reliable startup | Electron smoke test and AppImage check |
| Desktop security | Context isolation, sandboxing, blocked arbitrary navigation, allowlisted external link | Preserve or strengthen | Main-process inspection and smoke tests |
| Locales | English, Korean, Chinese, and Spanish (Argentina) static outputs | Preserve existing locales and add Catalan (`ca`) | Build-output validation and manual language checks |
| AppImage | AppImage-only Linux packaging | Preserve target and release workflow | GitHub Actions packaging |
| Packaging size | Maximum compression, source-map exclusion, artifact-size reporting | Preserve and measure changes | Workflow summary and artifact inspection |
| Release publishing | Manual/release-triggered AppImage build and release attachment | Preserve a reproducible release path | Release-candidate workflow |

## Review rule

Every implementation pull request must identify the rows it affects and state how those rows were validated. Unrelated rows should remain unchanged.
